# QA — CTA Audit & Regression Guard

This folder is the **CTA (Call-to-Action) regression harness** for the VitaCoreX
marketing site. It is the deliverable of [P17 Broken Buttons and CTA Audit](../../) and
is the authoritative answer to the user directive _"не работающие кнопки"_ (2026-04-19).

> **One-line contract**: every interactive element on every HTML page is
> inventoried, every target is validated (HEAD check + anchor resolve + handler
> presence), and the CI gate blocks any push that introduces a broken CTA.

## Files

| File | Role | Regenerated by | Hand-edited? |
|------|------|----------------|--------------|
| `cta-inventory.md` | Structured list of every `<a>`, `<button>`, `<input type=submit\|button\|image>`, `[role=button]`, `<form>` across all HTML pages. One row per interactive element. | `scripts/audit-ctas.js` | **No.** Regenerate only. |
| `cta-broken.md` | Subset of `cta-inventory.md` that failed target validation (HTTP 4xx/5xx external, missing internal file, missing anchor, no-handler button, malformed mailto/tel, etc.). One row per failure. | `scripts/verify-cta-targets.js` | **No.** Regenerate only. |
| `cta-triage.md` | Disposition per broken row: `fix` / `remove` / `defer` / `invalid`. The only hand-authored file in this folder. | Hand-authored by maintainer. | **Yes.** This is the decision log. |
| `README.md` | This file. | Hand-authored. | **Yes.** |

## Scripts

Both scripts live at the repo root under `scripts/` and use only Node built-ins
(no `npm install` required to run).

```bash
# 1. Regenerate inventory (must run before verify — see Stale Inventory Lesson below)
node scripts/audit-ctas.js        # writes docs/qa/cta-inventory.md

# 2. Verify every target in the inventory
node scripts/verify-cta-targets.js  # reads inventory, writes docs/qa/cta-broken.md
```

Or via npm scripts (from repo root):

```bash
npm run audit:cta    # = node scripts/audit-ctas.js
npm run verify:cta   # = node scripts/verify-cta-targets.js
npm run qa:cta       # = audit then verify (correct sequence)
```

## Exit codes

Both scripts follow the same convention:

| Exit code | Meaning | CI action |
|----------:|---------|-----------|
| `0` | Clean — no issues found | Build continues |
| `1` | Fatal error (unexpected exception; stack trace in logs) | Build fails; investigate script |
| `2` | Validation failure (unclassified rows for audit; broken rows for verify) | Build fails; triage required |

## CI gate

Wired in `.github/workflows/qa-cta.yml`. Runs on:

- Every `push` to `main` that touches `**.html`, either of the two scripts, or
  the workflow file itself
- Every `pull_request` with the same path filter
- Manual trigger via `workflow_dispatch`

Sequence (MUST be this order):

```
actions/checkout@v4
→ actions/setup-node@v4 (node 20)
→ node scripts/audit-ctas.js         # regenerate inventory    (exit 2 = fatal)
→ node scripts/verify-cta-targets.js # validate targets        (exit 2 = tolerated)
→ git diff --exit-code -I "^generated:" docs/qa/cta-inventory.md docs/qa/cta-broken.md
```

### Why the gate is a baseline-diff, not verifier exit code

The verifier exits `2` whenever broken rows exist in the inventory. The
baseline state already has **12 known-invalid-by-design rows** (10 Group D
`no-handler` + 2 Group C LinkedIn HTTP 999 bot-block — all triage-documented
in `cta-triage.md`). A pure-exit-code gate would fail every build. We need to
distinguish _"these 12 known rows"_ from _"someone just introduced a 13th"_.

The gate is therefore:

1. **Regenerate both baselines** (`audit-ctas.js` + `verify-cta-targets.js`).
2. **Diff them against the committed baselines**, ignoring the `generated:`
   timestamp via `git diff -I "^generated:"`.
3. **Any drift = fail.** Either a new broken row was added (bad), or an
   existing row was fixed/removed without the maintainer committing the new
   baseline (also bad — improvements must be locked in).

### Updating the baseline

When you intentionally change the CTA footprint (add a page, fix a broken
row, re-triage an invalid row), run `npm run qa:cta` locally and commit the
regenerated `docs/qa/cta-inventory.md` + `docs/qa/cta-broken.md` alongside
your HTML / triage change. CI will now be green against your new baseline.

### Artifacts on failure

On failure, the regenerated `cta-inventory.md` + `cta-broken.md` are uploaded
as artifacts for 30 days so maintainers can diff the pre-fail baseline.

## Stale Inventory Lesson (Step 17.4 post-fix protocol)

**CI always regenerates inventory BEFORE running the verifier.** This is not
optional.

During P17 Step 17.4 fix round (2026-04-20), the first post-fix verifier run
reported the same 22 broken rows as pre-fix despite 10 correct fixes having
been committed. Root cause: `scripts/verify-cta-targets.js` reads the
markdown-serialized inventory at `docs/qa/cta-inventory.md`, which is generated
by `scripts/audit-ctas.js`. The verifier has no direct view of the HTML source
tree. Running verify against a stale inventory re-checks targets that no longer
exist in source (or misses new rows that were added).

**Correct sequence** (enforced both in CI and locally via `npm run qa:cta`):

```
1. audit-ctas.js    → writes fresh cta-inventory.md from current HTML
2. verify-cta-targets.js → reads fresh inventory, writes cta-broken.md
```

**Wrong sequence** (silent failure mode):

```
1. edit some HTML
2. verify-cta-targets.js  ← reads STALE inventory, reports stale broken count
   (no error — just wrong data)
```

## Triage workflow

When CI reports a new broken row:

1. **Checkout the PR branch** (or pull the failing `main` commit locally).
2. **Download the CI artifact** (`cta-baselines-<run-id>` from the failed run)
   or regenerate locally: `npm run qa:cta`.
3. **Read `docs/qa/cta-broken.md`** — the new row will be in one of these reason
   buckets:
   - `external-http-4xx` — target URL returns 4xx on HEAD+GET (+ browser UA)
   - `external-http-5xx` — server error; usually transient, retry once
   - `external-http-opaque` — HTTP 999 (LinkedIn) or similar bot-block; NOT broken
   - `external-network-error` — DNS / timeout / TLS handshake
   - `internal-file-missing` — target HTML file does not exist in repo
   - `internal-anchor-missing` — file exists but `#fragment` has no matching `id`
   - `mailto-malformed` — invalid mailto syntax
   - `tel-malformed` — not E.164-ish
   - `no-handler` — `<button>` with no `onclick=`, no form, no `data-*`
     delegation signal. Often a false positive for `<button id="X">` wired via
     external JS `addEventListener`. Mark `invalid` if Step 17.5 Playwright spec
     proves wiring.
   - `unresolvable` — verifier cannot classify; investigate

4. **Decide disposition** and add a row to `docs/qa/cta-triage.md`:
   - `fix` — change href/onclick to correct target
   - `remove` — delete the CTA; if copy depends on it, rewrite the paragraph
   - `defer` — real feature gap; ship a disabled state + "coming soon" copy
   - `invalid` — false positive; document rationale + extend verifier to
     suppress in future (add regex/URL to ignore-list)

5. **Apply the fix**, run `npm run qa:cta` locally until green, commit.

6. **CI must return green** before merge. No `allow-failure` on this job.

## Scope boundaries

### What is a CTA (in scope)

- `<a>` with non-empty `href` (except `javascript:void(0)` placeholders)
- `<button>` elements (incl. `[type=submit]` and `[type=button]`)
- `<input type="submit|button|image">`
- `[role="button"]` elements with keyboard activation
- `<form>` submit targets (POST/GET action URLs)

### What is NOT a CTA (out of scope)

- JSON-LD `sameAs` URLs (structured data, not interactive). Tracked as
  Step 17.1 auditor-refinement follow-up, NOT a P17 blocker.
- Meta/link tags (`<link rel=canonical>`, hreflang, OpenGraph, etc.) — covered
  by `verify-sitemap.js` + canonical checks, not this harness.
- Image `src` / script `src` — asset loaders, not user-facing CTAs.
- Pure decorative elements with `tabindex="-1"` and no interactivity.

### Known invalid-by-design rows

- **LinkedIn personal page bot-block** — `/in/steven-miller-ab17783a5` returns
  HTTP 999 to non-browser UAs. Reachable in real browsers. Permanent
  `external-http-opaque` classification; do not attempt to "fix".
- **External-JS `addEventListener` handlers** — `<button id="X">` wired via
  `<script src="...">` cannot be traced by the HTML-only auditor (it would need
  a JS AST pass of the linked files). Behavioral proof is
  `tests/e2e/cta-click.spec.ts` (P17 Step 17.5). 10 such buttons are documented
  as `invalid · Group D` in `cta-triage.md`.
