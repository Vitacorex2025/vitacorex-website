# VCX Chat Attachments — Phase 7B

> Architecture doc | 2026-04-03 | Branch: `codex/phase2-safe-realign`

---

## Overview

Phase 7B adds structured attachment handling to the floating chat widget.
Files and images uploaded through the chat are classified, stored, and
acknowledged with honest, controlled responses. No fake analysis or
hallucinated content is generated.

---

## Attachment Categories

| Category | Extensions | MIME Prefix | Example |
|----------|-----------|-------------|---------|
| `document` | .pdf, .doc, .docx, .txt, .md, .csv, .xlsx, .xls | application/*, text/* | contract.pdf |
| `image` | .jpg, .jpeg, .png, .gif | image/* | photo.jpg |

Classification is by extension first, MIME fallback second.

## Backend Architecture

### Service: `chat_attachments.py`

| Function | Purpose |
|----------|---------|
| `classify_attachment(filename, content_type)` | Returns `"document"` or `"image"` based on extension/MIME |
| `type_label(filename)` | Human-readable type (e.g., "PDF document", "JPEG image") |
| `list_session_attachments(session_id)` | Lists all files in `uploads/chat/{session_id}/` with metadata |
| `build_attachment_summary(session_id)` | Builds summary string (e.g., "2 files attached: contract.pdf (PDF document)") |
| `attachment_acknowledgment(filename, category, type_label)` | Generates honest acknowledgment message per category |

### Enhanced Upload Endpoint

```
POST /api/legal-chat/upload
Response now includes:
  category:        "document" | "image"
  type_label:      "PDF document", "JPEG image", etc.
  acknowledgment:  Category-aware response message
```

### New Endpoint: Session Attachments

```
GET /api/legal-chat/attachments/{session_id}
Rate limit: 30/minute

Response:
  {
    "ok": true,
    "session_id": "...",
    "count": 2,
    "attachments": [
      {
        "file_id": "uuid",
        "filename": "contract.pdf",
        "category": "document",
        "size": 102400,
        "type_label": "PDF document"
      }
    ],
    "summary": "2 files attached: contract.pdf (PDF document), photo.jpg (JPEG image)"
  }
```

### Convert-to-Intake Integration

When `POST /api/legal-chat/convert-to-intake` runs, it now:
1. Calls `build_attachment_summary(session_id)`
2. If files exist, appends the summary to `doc_hint`
3. The intake form shows "Chat attachments: 2 files attached: ..."

## Frontend Behavior

### Image Uploads

1. User selects image (file picker or camera capture)
2. Client-side validation: extension, size, non-empty
3. Image thumbnail preview rendered in chat bubble (via `URL.createObjectURL`)
4. File uploaded to `POST /api/legal-chat/upload`
5. Server classifies as "image", returns acknowledgment
6. Bot message: honest acknowledgment that no image analysis is available
7. User is asked to describe what the image shows
8. Image will be included if user converts to intake

### Document Uploads

1. User selects document (file picker)
2. Client-side validation: extension, size, non-empty
3. Document icon with file pill rendered in chat bubble
4. File uploaded to server
5. Server classifies as "document", returns acknowledgment
6. Bot message: acknowledges receipt, notes no document reading in chat
7. Suggests Contract Review service for detailed analysis
8. Document included if user converts to intake

### Camera Capture (Mobile)

- Camera button triggers `<input type="file" accept="image/*" capture="environment">`
- On mobile, this opens the device camera directly
- On desktop, falls back to file picker (same as image upload)
- Captured photo follows the image upload flow

### Error Messages

| Condition | Message |
|-----------|---------|
| No file extension | "Please rename with correct extension" |
| Unsupported extension | Lists accepted document and image types |
| Empty file | "File appears to be empty" |
| File too large (client) | Shows size, limit, suggests compression |
| File too large (server 413) | "Server rejected as too large" |
| Validation failure (server 400) | Shows server error detail |
| Upload failed (network) | Suggests intake form instead |

## Controlled Fallback: No Fake Analysis

**Principle:** The system never pretends to analyze file contents it cannot read.

### Image acknowledgment:
> "Image received: photo.jpg (JPEG image).
>
> I cannot analyze images directly. If this image is relevant to your matter,
> please describe what it shows and I can help guide you.
>
> The image will be included if you convert to a structured intake."

### Document acknowledgment:
> "Document received: contract.pdf (PDF document).
>
> I cannot read document contents directly in chat. For full document review,
> consider our Contract Review service.
>
> This file will be included if you convert to a structured intake."

These are generated by `attachment_acknowledgment()` on the server and returned
in the `acknowledgment` field of `ChatUploadResponse`.

## Validation Rules

All rules inherited from `upload_validator.py`:

| Rule | Value |
|------|-------|
| Max size | 25 MB (configurable via `VCX_MAX_UPLOAD_MB`) |
| Allowed extensions | .pdf, .doc, .docx, .txt, .md, .jpg, .jpeg, .png, .gif, .csv, .xlsx, .xls |
| Blocked extensions | .exe, .bat, .cmd, .sh, .ps1, .js, .html, .htm, .php, .py, .rb, etc. |
| MIME validation | Lenient (text/*, application/*, image/* accepted) |
| Filename sanitization | Removes path separators, null bytes, control chars; truncates to 200 chars |
| Empty files | Rejected (400) |

Client-side validation runs before upload to provide immediate feedback.
Server-side validation is authoritative.
